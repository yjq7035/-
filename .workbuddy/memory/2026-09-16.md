## 大版本 6：排查「整个界面无法点击」+ 输入层/主循环加固

> 用户报障："整个界面无法点击现在，检查一下"。纯逻辑校验 211/0、canvas 参数 0 违规、渲染 48000 帧 0 异常——**说明问题不在业务逻辑，而在"吞触摸的路径"和"主循环能不能活下来"**。

### 修掉的 5 个真问题

1. **`game_core.loop()` 裸跑无 try/catch（最高危）**：`update()`/`draw()` 任一处抛异常 → `requestAnimationFrame(() => this.loop())` 永不执行 → 主循环彻底停摆。现象就是"画面定格 + 所有按压/波纹反馈消失 = 整个界面点不动"，而且日志里只有一次异常，很难和事故对上号。修：`try { update/draw } catch { 记一次日志 }`，**rAF 重新排帧必须放在 try 之外**，保证主循环不可能断链。
2. **拖放态悬空 → 首行 `return` 吃掉之后所有点击**：
   - 置位只有一处（`input.js` touchmove 里 `dragging = true`），但 `handleTouchEnd` 有**多个提前 return 分支不调用 `_resetDragState`**。最典型：拖拽途中 `update()` 把 lives 扣到 0 → `gameOver = true`，松手时走"结算界面"分支只 `releaseButton()` 就 return → `dragging=true pendingDrag=true touchStartPos=<非空>` 永久悬空。
   - 旧兜底守卫 `if (pendingDrag && !touchStartPos) _resetDragState()` 只救得了"起点丢了"那一半，**起点非空的那一半是永久死锁**。
   - 修：① 守卫改成**无条件**——收到新 touchstart 就说明上次手势已结束，直接清干净（单指流程不会误伤）；② 结算分支、顶栏分支各自显式补 `_resetDragState`。回归：猴子测试里该态从 **107 次 → 0 次**。
3. **输入层与渲染层对 `gameOver` 的口径不对称**：`renderer.render` 只在 `scene==='battle'` 才 `drawGameOver`，而 `input` 的 `if (game.gameOver)` **不看 scene**、无条件吞掉所有触摸 → 一旦出现"gameOver 但不在战斗场景"，屏幕不画结算界面、输入全被吃光。修：输入层两处都补 `game.scene === 'battle'`；另在 `loop()` 加**不变式修复** `if (gameOver && !gameWon && lives > 0) { gameOver=false; isRunning=true; }`，从结构上消灭这类死锁。
4. **`onVideoComplete()` 不恢复生命**：只复原波次+金币，`lives` 仍是 <=0 → 广告一结束、下一帧立刻又判负，玩家看 30 秒广告等于白看（"出广告就秒死"）。修：复活补到 `maxLives × 30%`（`REVIVE_LIVES_RATIO`）。
5. **`startBattle()` 静默 `return false`**：存档里 `selectedLevel` 是不可玩关卡（历史可玩→后改成"待扩展"，或坏档；`meta.normalize` 只校验 `>=1` 不封顶）时直接失败，而输入层照样弹绿色"开始游戏" → 玩家看到"点了完全没反应"。修：兜底切到第一个可玩关卡，并把输入层的假成功改成如实报错。

## 大版本 6 续：真正让"整个界面点不动"的那一刀 —— `ctx.roundRect` 缺失

### 线索来源：不在代码里，在配置文件里
`git status` 显示 `game.json` / `project.config.json` / `project.private.config.json` 都有**未提交的工作区改动**，而 `project.private.config.json` 把基础库从 **`3.17.2` 降到了 `3.14.0`**（`project.config.json` 同时把 `libVersion: latest` 钉成 `3.17.2`、并删掉了模板残留的 `worker: src/`）。**"现在"变坏 = 基础库版本被换掉了。**

### 反证（`.workbuddy/tools/noroundrect.js`）
造一个**没有 `ctx.roundRect`** 的 ctx 再画一帧：
```
★ 抛异常：TypeError: ctx.roundRect is not a function
  at drawSlots   (src/renderer.js:140:9)
  at drawBattle  (src/renderer.js:1505:3)
  at Object.render (src/renderer.js:1756:5)
  at Game.draw   (src/game_core.js:1545:14)
```
`roundRect` 是**很新**的 Canvas 2D 接口，低版本小游戏基础库没有它。而 `renderer.js` 里有 **25 处是直接 `ctx.roundRect(...)` 调用**（只有 `theme.roundRectPath` 内部做了 `typeof` 判断）。缺了它就**首帧 `draw()` 抛 TypeError** → 主循环的 rAF 链断掉 → **画面永远停在最初一帧、什么都不响应 = 用户说的"整个界面无法点击"**。这条把"配置改动 → 崩溃 → 症状"三者完整闭环了。

### 修法
- **`theme.polyfillRoundRect(ctx)`**：ctx 上没有 `roundRect` 时补一个（用 `quadraticCurveTo` 建圆角路径；语义对齐原生——**只往当前路径追加闭合子路径，不自己 `beginPath`**，否则调用方的 `beginPath→roundRect→fill` 会多出一条空路径；同时处理 `isFinite` 与半径钳制）。
- **在 `Game` 构造函数里、拿到 ctx 的第一件事就调用它** —— 一次补齐覆盖所有 25 个调用点，比逐个调用点写兜底可靠。`theme.js` 是零依赖模块，不会引入循环 require。
- 回归固化：`regress-ui.js` 新增 **U6**（5 条）—— 故意 `delete ctx.roundRect` 再走真实构造流程，断言"构造后已补齐 / 全场景渲染不抛异常 / 结算按钮照常点得动"。

### 入口 `game.js` 同期又变了一次（用户在真机上调启动时序）
12:04 的版本把 `requestAnimationFrame(boot)` 换成 `setTimeout(boot, 1)`，注释写明真实原因：
> 真机上微信框架会注入 `WAGamePerformanceUtilsSDK.js` 等子包并 monkey-patch `wx.createCanvas`，JS 顶层同步调用时其内部依赖的 `getSystemNanoTime` 可能还没就绪（jsbridge not ready）→ 直接崩溃。用 `setTimeout` 让 jsbridge 初始化先跑完。

我只在它之上加了 **`booted` 幂等保护**（`if (booted) return;`），没有改动它的时序逻辑 —— 防止模块被重复求值（热重载）时建出第二个 Game（第二套全局触摸监听 + 画在离屏 canvas 上）。

### 结论口径（下次排查照这个顺序走）
1. **先看 `git status` / 配置文件改动**：基础库版本、`compileType`、`worker` 这类字段一变，症状可能和代码毫无关系。
2. **怀疑"整块点不动"时，先去数"哪些新 API 被直接调用而没做能力判断"**（`roundRect` / `ellipse` / `filter` / `setLineDash`…）。跨版本兼容的项目，新 API 一律要兜底或先 polyfill。
3. **主循环必须 try/catch**（见上一节），否则任何一个分支炸一下就是永久冻屏。

## 大版本 7：真机「一直卡在原生启动页」—— 入口重试循环自己造出来的坑

### 症状与判据
真机测试号启动后永远停在微信原生启动页（带小游戏 logo 那屏），不报错、不白屏、就是不动。
**判据只有一条：原生启动页的消失条件 = 主屏 canvas 画出第一帧。** 所以"卡启动页"等价于
「主屏 canvas 绘制指令 = 0 条」。这与过去的"整个界面点不动"是**两个不同**的故障：
- 点不动 = 已出画面，主循环停摆（roundRect / 帧异常）
- 卡启动页 = 一个像素都没出去（画布拿错 / ctx 为 null）

### 根因：`tryBoot` 重试循环把"崩溃"变成了"静默画到看不见的画布"
旧入口为解决 `WAGamePerformanceUtilsSDK` 注入竞态写了重试循环，但**兜错了地方**：
1. 竞态发生在 `wx.createCanvas()` **内部**（SDK 的 patch 调 `getSystemNanoTime` 抛 TypeError），
   赋值没完成 → `canvas` 仍是 null；
2. 下一次重试**又调了一次 `wx.createCanvas()`**；
3. 微信硬规则：**只有第一次调用返回屏幕画布，之后每次都是离屏画布**；
4. 于是重试"成功"、日志打出「✅ 启动成功」，但整局画在看不见的离屏画布上 → 主屏 0 像素。
过去那条 `if (!canvas)` 幂等缓存**救不了这个场景** —— 它只保护"createCanvas 成功之后"的失败。

### 反证（`.workbuddy/tools/entry3.js`，已并入 `_runall.js`）
| 场景 | 旧入口 | 新入口 |
|---|---|---|
| SDK 竞态 t<400ms | createCanvas **3 次 → 离屏**，主屏 **0** ❌ | **1 次 → 主屏**，主屏 **1074** ✅ |
| SDK 竞态 t<1200ms | **5 次 → 离屏**，主屏 **0** ❌ | **1 次 → 主屏**，主屏 **1074** ✅ |
| 缺 setLineDash | 半张（492 条后抛异常） | **1074** ✅ |
| getContext 返回 null | 假报"✅启动成功"、静默黑屏 | 同画布重试 6 次 + 明确报错，不撒谎 |

### 修法
- **`game.js` 重写启动流程**：`scheduleBoot` 先做 jsbridge 就绪探测（`wx.getPerformance().now()`，
  副口 `wx.getWindowInfo`），最早 `BOOT_MIN_DELAY=250ms` 才动手，探测间隔 25ms、上限 1.5s 硬上。
  **`wx.createCanvas()` 全生命周期必须且只能调用一次**；`ensureCanvas` 里绝无"失败就重建"的循环，
  只在首次失败时给唯一一次补救机会并**大声警告**（第 3 次直接拒绝）。
- **`canvas` 与 `ctx` 分开判空**：过去 `ctx` 的创建被塞在 `if (!canvas)` 分支里，一旦 `getContext`
  返回空（jsbridge 未就绪）就永远是 null，之后每帧抛异常、0 像素。现在同画布重试。
- **`theme.polyfillCanvas2D(ctx)`**：在 `polyfillRoundRect` 之上补 `setLineDash`（降级实线）
  与 `ellipse`（外接圆近似）。`Game` 构造改为调用它。
- **`game_core.loop()` 首帧异常单独喊话**：`_frameCount<=1` 时打「💀 首帧绘制失败 → 卡在原生启动页」，
  不再和"后面某帧抽风"混在同一条不痛不痒的日志里。
- 日志里「✅ 启动成功」现在会带上 `createCanvas 共调用 N 次，应为 1`，假成功一眼可见。

### 关键教训（下次排查照这个走）
1. **"卡启动页"先数 `wx.createCanvas()` 被调了几次**：>1 且首帧无像素 = 画到离屏画布上了。
   这是"兜竞态"类重试最容易踩的坑 —— 重试的动作本身就是错误的。
2. **重试必须区分"可重试阶段"**：`createCanvas` 是**一次性**资源，绝不能进重试循环；
   可重试的只有它之后的步骤。
3. **失败要吵**：`game.js` 曾经在 0 像素的状态下打印「✅ 启动成功」，把故障藏了一整轮排查。
4. 调参旋钮：真机若仍偶发，调大 `BOOT_MIN_DELAY`（400~600）。
5. 回归：`node .workbuddy/tools/entry3.js` → 38 通过 / 0 失败；
   `syntax 22/22`、`verify 211/0`、`regress-ui 35/0` 仍全绿。

### 环境备忘（复用旧结论）
本机 Git Bash 连 `ls`/`dirname`/`mkdir` 都没有（只剩 shell 内建）；`cd <路径> && node -e "..."`
仍可用。临时对照文件要写**项目根目录**（相对 require `./src/...` 才能解析），用完立刻
`fs.unlinkSync` 清掉。
