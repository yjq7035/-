先读这一段：v1 的结论是错的

v1 把根因写成了「启动重试循环拿错了画布（画到离屏画布上）」。真机日志到手后可以确定： 那个归因不成立。

日志里 wx.createCanvas() 第 1 次、第 2 次都是直接抛异常， 并不是「第 2 次成功返回了离屏画布」。真正的根因是工具环境级故障。

v1 里那条硬规则（createCanvas 全生命周期只调一次）本身没错、予以保留， 但「为什么卡住」的定性必须更正 —— 错误的注释会让下一次排查沿着错方向再爬一遍。

一、结论

微信开发者工具「真机调试」注入的性能桩缺 getSystemNanoTime， 导致手机微信客户端基础库的 WAGamePerformanceUtilsSDK 一构造就 TypeError； 而 wx.createCanvas() 与 wx.getPerformance() 共用这个底层纳秒计时接口， 于是它们一起抛错 → 首帧画不出来 → 原生启动页永不消失。

一句话：这是工具的 Bug，不是你的代码。 同一份代码在 预览 / 体验版 / 正式版 下都正常，只有「真机调试」挂。

原生启动页的消失条件只有一个：主屏 canvas 画出第一帧。 所以「卡启动页」的等价形式是「主屏 canvas 绘制指令 = 0 条」。

整个栈都在 WAGame.js / WAGamePerformanceUtilsSDK.js 里。 这是最强信号：该去查报错原文，而不是改自己的启动逻辑。

2
createCanvas 每次必抛，不是「第二次拿到离屏画布」 
[boot] 调用 wx.createCanvas()（第 1 次）...

两次同一个错。重试毫无意义 —— 环境是坏的，不是"还没准备好"。

3
基础库是 3.17.2，不是 3.14.0 
[wxapplib]] Wechat Lib:3.17.2, 2026.9.8 20:10:23

所以上一轮"真机跑的是 3.14.0 老基础库"这个前提也不成立。 关键认知：project.private.config.json 里的 libVersion 只管模拟器； 真机调试 / 预览用的是手机微信客户端自带的基础库。别再拿那个字段解释真机现象。

4
开发者工具的性能检测注入只成功了一半 
[wxapplib]] inject subPackage: WAGamePerformanceUtilsSDK.js coast: 8
[DETECT EVENT] minigame detect tool inject!!
[DETECT EVENT] enable=true, autoStart=true
[wxapplib]] [Trace] TraceGlobal not found

性能事件采集器被注入了（enable=true, autoStart=true）， 但它依赖的宿主对象没到位 → 初始化即炸。这就是根因现场。

四、判据速查（三条同时成立即可定案）

① 栈的归属

报错栈全部落在 WAGamePerformanceUtilsSDK.js / WAGame.js，没有一帧是本工程代码。

② 接口共病

wx.createCanvas() 与 wx.getPerformance() 一起抛错 —— 它们共用底层纳秒计时口。

③ 环境差异

模拟器 / 预览 / 体验版正常，只有「真机调试」挂。

反面（另一类故障）

若 createCanvas 被调用 >1 次且首帧无像素 → 那才是"画到离屏画布"。

八、方法论教训（比修复本身更值钱）

  1. 「报错栈里一帧都不是自己的代码」= 立刻去查报错原文，别改自己的启动逻辑。 这次两条佐证都是直接搜错误串搜到的，五分钟定案；上一轮在自家代码里绕了整整一轮。
  2. 探针不能和故障源是同一个东西。拿被 Bug 打坏的 getPerformance 去探测 "环境好没好"，逻辑上就是自证循环 —— 永远探不通，还掩盖真相、误报成 「jsbridge 探测超时」（jsbridge 其实是好的）。
  3. 一次性资源绝不能进重试循环。createCanvas 就是典型：等待要放在它之前， 重试绝不能放在它之后。
  4. 失败要吵。静默黑屏是最贵的故障 —— 它让你多花一整轮去猜。 现在启动失败会弹原生 showModal，把原因和处置办法直接摆到屏幕上。
